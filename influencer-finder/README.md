# Villa Lithos Influencer Finder: core engine

Autonomous Instagram influencer intelligence and booking platform for Villa Lithos
(Porto Rafti, Attica). Objective: find the Instagram accounts most likely to generate
booked nights between November and April, with traceable evidence, and recommend the
partnership to offer. Not reach, not followers.

This folder holds everything that is platform-independent and testable:

| Path | What |
| --- | --- |
| `src/pipeline/types.ts` | Data model: candidate, evidence, events, classification, private insights, scores, provenance |
| `src/config/villa.ts` | Property profile and commercial defaults (unverified items flagged) |
| `src/discovery/queryGenerator.ts` | Dynamic query engine: 1,100+ queries from event type × month × destination × market × language × intent; lane-balanced capping; deterministic ids for resume |
| `src/discovery/normalize.ts` | Handle extraction (profile URLs, titles, extracted post text), follower parsing, market/language guess, candidate merge, dedupe |
| `src/scoring/weights.ts` | Default weights, normalisation to 100 |
| `src/scoring/score.ts` | 0–100 fit score, confidence, tier gates (no winter evidence → no Tier A), red flags, contradictions |
| `src/scoring/budget.ts` | Venue budget estimate (participants × price × venue share, floor-price check, scenarios) |
| `src/scoring/ebn.ts` | Expected booked nights (primary) and expected net value (secondary), conservative/base/optimistic |
| `src/insights/rescoring.ts` | Private-insights rescoring: keeps the public score, computes derived metrics, explains the delta |
| `src/outreach/generator.ts` | Track recommendation, EN/HE drafts from real facts, insights-request message, no-price guard |
| `src/ai/prompts.ts` | Claude prompts (screening / deep / insights extraction), JSON schema, model tiers |
| `supabase/migrations/0001_schema.sql` | Full schema: runs, resumable query plan, candidates, evidence, events, score history, private insights, outreach, feedback, learning, RLS, private storage bucket |
| `supabase/functions/*` | Deno edge functions: `run-discovery` (resumable, spend-capped), `classify-candidates`, `analyze-insights`, `generate-outreach`, `export-csv` |
| `tests/engine.test.ts` | 33 tests covering generator, handle cleaning, website dedupe, weights, scoring gates, budget inputs, season-window EBN, affordability, rescoring, track choice, outreach wording and gender forms |
| `data/run-2026-10-15/` | First real discovery run: 200 queries, raw Tavily responses, 339 accounts, classifications, `ranked.json`, `ranked.csv`, `REPORT.md` (Best Match + 9 with evidence), `seed.sql` |

Rebuild the run outputs from the files on disk (no network calls):

```
python3 -I scripts/merge-slices.py        # candidates-slice-*.json -> candidates.json
python3 -I scripts/merge-classified.py    # classified-batch-*.json -> classified.json (validates evidence URLs)
npx tsx scripts/rank-dataset.ts           # -> ranked.json (scores, EBN, budget, track, drafts)
python3 -I scripts/make-report.py         # -> REPORT.md
python3 -I scripts/export-ranked-csv.py   # -> ranked.csv
npx tsx scripts/seed-sql.ts               # -> seed.sql for the Cloud database
```

Deployment set for Lovable Cloud: `python3 -I scripts/build-lovable-bundle.py OUT_DIR` merges `src/` into one
module `supabase/functions/_shared/engine.ts` and points the edge functions at it. Before upload it was checked
with `deno check` on all six functions and against `src/` on all 339 run candidates (scores, tracks and Hebrew
drafts identical).

```
npm install
npm test            # vitest
npm run typecheck
npm run queries 400 out.json   # print a query plan
./scripts/sync-shared.sh       # copy src → supabase/functions/_shared/engine
```

## Live deployment (Lovable Cloud)

- Project "Villa Scout": https://lovable.dev/projects/da63c33b-c267-43d0-bab4-555873891dd6 (TanStack Start app, Lovable Cloud database).
- Database: `supabase/migrations/0001_schema.sql` applied directly; seeded with `data/run-2026-10-15/seed.sql`
  (fetched by the database itself from a commit-pinned URL and checked by SHA-256 before execution). Counts in the
  cloud match the local verification: 339 candidates, 378 evidence rows, 353 events.
- Server code: Lovable TanStack projects cannot add Supabase edge functions, so `deploy/lovable/src/server/lithos/**`
  (generated by `scripts/build-lovable-node.py`) is served at `POST /api/lithos/<function>`; each file was copied
  with its SHA-256 verified. The UI calls it through `callLithos()` with the owner's session token.
- Still needed from the owner: `TAVILY_API_KEY` in Project Settings, Secrets; the owner user in Cloud, Users;
  public sign-up disabled in Auth settings. Signed-in QA follows once the owner account exists.

## Verification done in the build session

- `npm test` (33 tests) and `npm run typecheck` pass; every edge function passes `deno check` with the synced engine.
- The schema migration and the generated seed were applied to a local PostgreSQL 16 with minimal stand-ins for the Supabase `auth` and `storage` schemas. Both apply twice without errors and with identical row counts, so they are idempotent.
- Undated events are deduplicated by a `nulls not distinct` unique key (Postgres 15 or later), so re-classifying a candidate cannot inflate its events per year or its Expected Booked Nights.
- Row-level security: a signed-in user reads all rows, an anonymous request reads none.

## Security model

Single owner. RLS grants full access to any authenticated user, so public sign-ups must be
disabled once the owner account exists. API keys live only in server-side secrets used by the
edge functions; the browser never sees them. Outreach is drafted, never sent.

## Sources

| Source | Status | Note |
| --- | --- | --- |
| Tavily | enabled when `TAVILY_API_KEY` is set | Instagram-focused search (profiles, posts, reels) + extract for author resolution and event pages |
| Instagram Graph API | needs credentials | Business Discovery enriches known Business/Creator handles (followers, media count, bio, website, recent media). Hashtag Search returns media without author usernames and is capped at 30 hashtags per 7 days. Neither exposes third-party audience insights. |
| Apify | needs approval | Not used; costs, reliability and platform-terms exposure must be approved first |
| Private uploads | enabled | Screenshots, PDFs, exports, media kits, sales reports; stored in a private bucket |

## Provenance

Every stored number carries one of: `verified_public_fact`, `evidence_supported_inference`,
`influencer_reported`, `document_backed`, `independently_verified`, `ai_estimate`, `unknown`.
A screenshot is `document_backed`, never `independently_verified`. Booking probabilities are
`computed_not_verified` until outcomes exist.
